## 2. 四个必须先知道的事实（含证据）

### 2.1 数据是"每个人各有一个树洞"——这是核心缺口

```ts
// 树洞 src/App.tsx
const STORAGE_KEY_SCROLLS = 'aot_levi_hange_scrolls_v2';   // :27
const STORAGE_KEY_MY      = 'aot_levi_hange_my_v2';        // :28
// 读：:34 / :48   写：:68 / :74  —— 全部 localStorage
```

后果：
- 你投的卷轴，**只有你自己能看到**；
- 「点击拾取」抽的是**你自己浏览器的**数组（`App.tsx:109-113`），不是别人的；
- 换设备 / 清缓存 / 换浏览器 = 全部卷轴消失。

> 这不是 bug，是这个包本身的形态：它是一个**纯前端单机 demo**。`metadata.json` 里虽然声明了服务端 Gemini 能力，但代码里没有任何调用。

## 3. 嵌合方案（三选一）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. iframe** | 树洞单独构建 → 产物放 `public/treehole/`；主站新增第 5 个 tab，`<iframe src="/treehole/index.html">` | **零 CSS / JS 冲突**（第 2.2 节三个问题全部自动消失）；与现有「塔塔开」分区**完全同构**；树洞保留自己的暗色像素主题；主站首屏体积不变 | 与主站音效各自独立，需注意双重播放；iframe 内部内容不被搜索引擎索引 | ✅ **推荐** |
| **B. 源码合并** | 整体搬进 `src/components/treehole/`，作为 tab 组件渲染 | 一体感最好；可共用主站 `soundManager`；无 iframe 尺寸问题 | 需逐一隔离 3 处全局 CSS；**暗色像素主题 vs 主站浅色羊皮纸**在观感上割裂；+908KB 背景图进主 bundle；`src/utils/audio.ts`、`src/types.ts` 等**文件名直接撞车**，必须整体改名放到 `treehole/` 命名空间 | 除非你要深度重做视觉 |
| **C. 独立子域名** | 单独部署，主站只放外链 | 完全解耦 | 脱离"嵌进导航栏"的需求 | ✖ |

## 4. 核心功能设计：投放 / 拾取 / 永久保存

### 4.1 三个动作的语义定义

| 动作 | 语义 | 现在的实现 | 目标实现 |
|---|---|---|---|
| **投放** cast | 写一张卷轴丢进树洞 | 塞进**自己的** localStorage 数组（`App.tsx:93-97`） | 写入**共享**存储，全员可见 |
| **拾取** pick | 从树洞摸出一张读 | 从**自己的**数组里随机抽（`App.tsx:100-122`） | 从**共享池**里抽一张**自己没读过**的 |
| **永久保存** persist | 卷轴不因清缓存/换设备而消失 | 清缓存即全没 | 存服务端，长期保留 + 可导出备份 |

### 4.2 拾取的关键设计：一次性还是可重复？

| 方案 | 行为 | 评价 |
|---|---|---|
| (a) 完全随机、不记录 | 每次从全池随机抽 | 池子变大后，**旧卷轴会被概率淹没**，很多心事永远没人读到 |
| (b) 一次性消耗（捡走即消失） | 抽走即从洞里删除 | 与"永久保存"**直接冲突**。且会让人不敢投递（怕被陌生人拿走） |
| **(c) 不消耗 + 未读优先** | 每次抽一条**当前设备未读过**的；全部读完后再提示"重读" | ✅ **推荐**。既保住"永久保存"，又保证**每条卷轴都有机会被读到**，且每次拾取都是新鲜感 |

(c) 的实现方式：前端把"已读 id 列表"随请求带上，服务端返回一条不在其中的（`ORDER BY createdAt DESC` 采样 + `NOT IN`）。已读列表上限设 500 条即可（体量大了再换成服务端的 `picks` 集合 + 唯一索引）。

### 4.3 数据模型（草案）

```ts
interface TreeHoleScroll {
  id: string;              // 服务端生成
  content: string;         // ≤ 200 字（沿用 WriteScrollModal.tsx:149 的现有上限）
  author: string;          // ≤ 16 字（沿用 :170），空则"巨木森林同行者"
  category: 'secret' | 'miss' | 'wish' | 'release' | 'whisper';
  createdAt: number;       // 服务端时间，防篡改
  likes: number;           // 献出心脏计数
  steam: number;           // 送热汤计数
  status: 'visible' | 'hidden' | 'deleted';
  deviceHash: string;      // 匿名设备标识的哈希（**不存 IP、不存原文**）
  reportCount: number;
}
```

> 隐私红线：树洞的立命之本是"匿名"，**不记录 IP、不记录 UA、不记录设备指纹**，只保留一个不可逆哈希用于限流与"我的卷轴"。这一条建议写进站点声明。

### 4.4 为什么不能沿用 `archive.json` 那一套

现有的同人本归档是"云函数读整个 JSON → 改 → 写回"（`cloudbase/functions/admin-upload/index.js` 的 `readArchive` / `writeArchive`）。**单管理员低频写入没问题，公开匿名高频写入会丢数据**：

| 方案 | 并发写 | 查询能力 | 删除单条 | 适用 |
|---|---|---|---|---|
| COS 单个 JSON | ❌ 读-改-写竞态，**同时两人投稿必丢一条** | ❌ 只能全量拉 | ❌ 要重写整个文件 | 仅单写入者（现有管理通道） |
| **CloudBase 云数据库（文档型）** | ✅ 原子 `add` | ✅ 索引 + 分页 + 按分类筛选 | ✅ 按 id 删 | ✅ **推荐** |
| CloudBase MySQL | ✅ | ✅ | ✅ | 对这个体量是过度设计 |

### 4.5 接口草案

统一走**云函数**（沿用已跑通的 **Event 函数 + HTTP 访问服务** 模式，**不要加 `--httpFn`**），浏览器不直连数据库。

| action | 入参 | 出参 | 鉴权 |
|---|---|---|---|
| `cast` | `content, author, category, devicePass` | `{ id }` | 设备通行证 |
| `pick` | `excludeIds[]`（≤500） | `{ scroll \| null }` | 设备通行证 |
| `listMine` | `devicePass` | `{ scrolls[] }` | 设备通行证 |
| `react` | `id, kind:'like'\|'steam', devicePass` | `{ likes, steam }` | 设备通行证（**一人一次**） |
| `report` | `id, devicePass, reason` | `{ ok }` | 设备通行证 |
| `admin:list` / `admin:setStatus` / `admin:export` | 管理员口令 token | — | 管理员口令 |

服务端必须做的四件事：
1. **长度与频率校验** — 每 `deviceHash` 例如 10 分钟内最多 3 条〔阈值待定〕；
2. **敏感词过滤** — 落库前拦一道；
3. **只写服务端时间** — 不信客户端 `timestamp`（现有 `WriteScrollModal.tsx:38` 用的是 `Date.now()`，可伪造）；
4. **一人一赞** — 用 `deviceHash` 去重，否则一个人能把 `likes` 刷到 9999。

## 5. 是否要上 QQ / 微信登录

### 结论：**不要上。**

### 5.1 产品理由（最重要）

树洞的全部价值来自**"匿名才敢说"**。留言内容大概率是心理向、同人圈内的私密心事。一旦要求登录：

- 用户会立刻**自我审查**，最需要树洞的那部分内容直接消失；
- 而且 QQ / 微信带来的**不是匿名，是最彻底的实名化**——账号背后是真实手机号与真实社交关系链。对一个"深夜树洞"来说，这是**功能上的自相矛盾**。

### 5.2 资质理由（这可能是决定性的）

| 通道 | 主体要求 | 费用 | 对个人主体可行性 |
|---|---|---|---|
| 微信网页授权（H5 登录） | **必须是非个人主体**完成微信认证的**服务号** | 300 元/年 | ❌ **不可行**。微信官方明确：个人主体不支持微信认证，个人服务号不支持网页授权 |
| 微信开放平台「网站应用」 | 需已认证服务号 + 开放平台开发者资质认证 | 再 300 元/年 | ❌ 第一步就卡住 |
| QQ 互联「网站应用」 | 网站地址与回调地址**需在工信部完成备案**，且与平台填写信息一致 | — | ❌ 当前站点跑在腾讯测试域名 `*.tcloudbaseapp.com` 上，**无法备案**。绑自定义域名 + 走完备案是前置条件 |

> 来源：微信开放社区官方答复「只有完成企业认证的服务号（以及政府机构类型、媒资主体类型的公众号）才具备网页授权功能」；微信服务市场「个人服务号不支持网页授权功能」；QQ 互联《网站审核规范》「网站地址及回调地址需在工信部完成备案」。

也就是说，这**不是"要不要"的选择题，而是"能不能"的资格题**。

### 5.3 技术理由

登录不是加一个按钮，而是要引入：OAuth 回调域名维护、`access_token`/`refresh_token` 生命周期、用户表、会话、注销与数据删除、风控——工程量至少翻数倍。而我们真正想要的"防滥用"，靠下面的轻量机制就能拿到 80% 的效果。

### 5.4 替代方案：无感设备身份（复用已跑通的模式）

- 首次访问时前端生成随机 `deviceId`（UUID）存 localStorage，向后端换一枚**签名通行证**；
- 服务端用 **HMAC + 过期时间**签名，校验时 `timingSafeEqual` 比对 —— 这套 `signExp / verifyToken / safeEqual` 已经在 `cloudbase/functions/admin-upload/index.js` 里**实测跑通**，直接搬；
- 能力：区分"我的卷轴"、一人一赞、频率限流、删除自己的卷轴；
- 成本：≈ 0（无第三方账号、无审核、无密钥托管）；
- 边界：清缓存 / 换设备就换身份。**对树洞来说这个"不可靠"恰恰是优点**——它天然不支持跨设备追踪。

### 5.5 如果之后确实需要"只给群友"

三档软门槛，按骚扰量逐步升级，**都不需要登录**：

| 档 | 机制 | 成本 | 何时启用 |
|---|---|---|---|
| **L0** | 完全开放，仅靠限流 + 敏感词 + 举报 + 管理删除 | 最低 | **建议起步就在这里** |
| L1 | **群口令**：一个共享口令写进群公告，前端校验一次后发通行证 | 低 | 出现站外扫站骚扰时 |
| L2 | **邀请码**：一码一用，管理侧生成 | 中 | 出现有组织刷屏时 |

> 群本身就是一道天然门槛（站点主要从 QQ 群引流），L0 大概率够用。

### 5.6 但管理出口是**必须**的

匿名开放写入 + 没有审核出口 = 迟早出事。至少要有一个隐藏管理入口，能：看到全部卷轴、按状态过滤、删除违规、看待举报、**一键导出全量 JSON**。复用现有 `ADMIN_PASSWORD` 口令模式即可。

## 6. "永久保存"的真实边界

| 风险 | 现状 | 建议 |
|---|---|---|
| **平台到期** | CloudBase 环境是**体验版，到期 2027-03-13**〔依项目记录，请到控制台复核〕 | 到期前升级付费版，或把数据整体迁走。"永久"目前实际是"到 2027-03-13" |
| **内容合规** | 匿名开放写入，腾讯云对托管内容有审核要求 | 落库前敏感词过滤 + 管理侧人工删除 + 举报入口。否则站点被举报封禁，"永久"就成空话 |
| **无备份** | 现有同人本也是单份 JSON | 管理侧"**导出全部 JSON**"，定期手动存一份到 GitHub / 本地 |
| **被锁定** | 数据模型强耦合某个后端 | 保持**扁平 JSON 可导出**的模型（4.3 节），保证将来能整体搬走 |
