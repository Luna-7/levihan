① 现状的 q0.92 高于源图质量，重编码反而让体积涨了 15%。
源图本身是 JPEG（质量约 q80），再用 q0.92 重新编码，等于要求编码器保留比原图更多的细节（包括原图的压缩噪声），于是 661,677 B → 761,348 B。
② PNG 无损通道是真正的体积杀手。
同一张图以 PNG 存入 PDF 是 2.01 MB（330%）。原因是画面里大量 网点（screentone） —— 高频抖动纹理的熵极高，PNG 的 Flate 字典压缩对它几乎无效。
若源图是 PNG 截图，会命中这条分支，几十页就能把 60 MiB 闸门撑爆。
③ 对已经是 JPEG 的源图，「原字节直通嵌入」是零损失最优解。
实测 661,677 B → PDF 664,966 B，开销只有 3,289 B —— 证明 jsPDF 走的是 DCTDecode 直通，没有二次重编码。
即：不降采样时，完全没必要过 canvas。省掉解码 + 重编码，体积不涨、画质不掉、速度还快得多。

对 67.71 MB 那次报错的推算

闸门拦在 输入图片原始体积之和 > 60 MiB。以本次样图 646 KB/页 为基准：

页数输入（原始文件）现状产出 PDF长边1200 q0.85
40 页25.9 MB29.0 MB14.1 MB
70 页45.3 MB50.8 MB24.7 MB
105 页67.7 MB76.2 MB37.1 MB

→ 若源图是 PNG 截图，输入更小、页数更少就会触闸（PNG 单页 2–3 MB，二三十页即到 60 MiB）， 且现状产出体积会是输入的 3 倍以上。

建议的改法（纯前端，不动云函数）

1. JPEG 源且长边 ≤ 上限 → 原字节直通嵌入

用 FileReader.readAsDataURL(file) 拿到原始 JPEG dataURL 直接 addImage，完全绕过 canvas。
收益：消除 15% 膨胀 · 画质 100% · 省掉解码重编码（大文件能快好几倍）。

2. PNG 源或超尺寸 → 才过 canvas，且输出一律 JPEG

把 isPng 分支从「按源格式选无损」改成「只有真带 alpha 的图才输出 PNG，其余一律 JPEG」。
仅这一步就能把 PNG 源从 2.01 MB/页 拉到 649 KB/页（3.1 倍）。

3. 引入「内页长边上限」

把 MAX_PAGE_PX: 12000（形同虚设，正常页永远小于它）改成一个真正生效的目标长边，建议 1600（保守）/ 1200（推荐）。

4. 质量默认值 q0.92 → q0.85

0.92 高于多数源图质量，只会白涨体积。同尺寸下 0.92 比 0.85 多占 24%。

5. 闸门从「输入体积之和」改成按输出预估

输入体积与输出 PDF 体积关系很弱（同样 646 KB 的输入，产出可以在 202 KB ~ 2.01 MB 之间）。 更合理的是按 页数 × 目标长边² 的像素预算估算，或边处理边累计输出体积。

⚠️ 但压缩只解决「能不能开始处理」，不解决「能不能传上去」。
云函数中转通道（vaultUpload）受 MAX_BODY = 6 MiB 请求体限制，叠加 Base64 的 4/3 膨胀， 只能吃 ≤ ~4.4 MiB 的 PDF。几十页的漫画在它面前画质必然崩。
→ SDK 直传通道（cosCredential）才是唯一现实路径，压缩参数只是让处理能起步、上传不至于太慢。
